# 설계

## 무엇을 만들고 있나

기획 에이전트의 파이프라인은 이렇게 흐릅니다.

```
기능·정책 → IA ─┬─→ 화면 스펙 JSON ──→ 렌더러 ──→ 화면
                │        (AI가 생성)              ↑
                └─→ 앱 셸 구조                    │
                                                  │
서비스 성격 ────→ 스킨 표 ──────→ 생성 함수 ───────┘
                    (AI가 생성)      (결정론적)
```

이 레포는 오른쪽 절반 — 렌더러가 조립할 부품과, 부품에 입힐 토큰 체계입니다.

AI는 두 곳에만 개입합니다. 화면 스펙과 스킨 표. 둘 다 형식이 정해진 데이터이므로
검증할 수 있고 재현됩니다. 나머지는 기계적 변환입니다.

## 핵심 결정 1 — 공유하는 것은 마크업이 아니라 계약이다

렌더링된 HTML 구조를 공유 대상으로 삼으면 "공통 컴포넌트 사용"과
"디자인 100% 변경"이 정면으로 충돌합니다. 디자이너가 배치를 바꾸는 순간
공유가 깨지고, 공유를 지키려면 디자인을 못 바꿉니다.

그래서 공유 대상을 계약으로 정의합니다.

> `stat-card`는 라벨 1개, 값 1개, 증감 표시 1개, 아이콘 1개를 담는다.

세로로 쌓든 가로로 놓든 아이콘을 왼쪽에 두든 계약은 동일합니다.
계약을 공유하면 디자인이 자유로워지면서 공통성은 오히려 강해집니다.
IA에서 생성한 화면 스펙이 디자인 단계에서 한 글자도 바뀌지 않기 때문입니다.

## 핵심 결정 2 — 컴포넌트를 4개 축으로 분해한다

```
컴포넌트 = 계약(고정) + 레이아웃(교체) + 스킨(교체) + 밀도(교체)
```

**계약** — 슬롯의 이름·개수·타입·필수 여부. 화면 스펙이 참조하는 유일한 대상.

**레이아웃** — 슬롯을 공간에 배치하는 방식. 컴포넌트 코드에 박지 않고
프리셋으로 뽑아낸다. 디자이너의 구조 변경 요구 대부분이 여기서 흡수된다.

**스킨** — 색·타이포·모서리·그림자·테두리·모션. 순수 값의 집합.

**밀도** — 여백 스케일. B2B 관리 도구와 B2C 랜딩은 같은 컴포넌트라도
밀도가 완전히 다르다. 별도 축으로 빼두면 브랜드마다 재작업하지 않는다.

## 핵심 결정 3 — 토큰 3계층

2계층으로는 "브랜드는 버튼만 완전히 둥글게, 카드는 각지게" 같은 요구에서 막힙니다.

```
Tier 1 원시     --gray-500, --space-unit        리터럴 값이 존재하는 유일한 계층
                  ↓
Tier 2 의미     --t2-surface, --t2-border       컴포넌트가 읽는 계층
                  ↓
Tier 3 컴포넌트 --t3-button-radius              컴포넌트별 최종 개입 지점
```

Tier 3가 100%의 열쇠입니다. 컴포넌트별 개입 지점이 열려 있으므로
어떤 디자인 요구도 토큰 값으로 흡수됩니다.

컴포넌트는 Tier 2와 Tier 3만 읽습니다. Tier 1을 직접 읽지 않습니다.

## 핵심 결정 4 — AI에게는 자유도가 아니라 제약이 필요하다

디자인을 사람이 아니라 AI가 만든다면 요구가 뒤바뀝니다.

| | 사람이 스킨 작성 | AI가 스킨 작성 |
| --- | --- | --- |
| 필요한 것 | 자유도, 편집 편의성 | 좁은 선택지, 검증 가능성 |
| 위험 | 손이 많이 감 | 자유로우면 매번 어긋나고 촌스러워짐 |

AI에게 CSS를 자유롭게 쓰게 하면 색 조화가 깨지고 여백이 들쭉날쭉해지고
실행할 때마다 다른 결과가 나옵니다.

그래서 스킨을 CSS가 아니라 **값이 채워진 표**로 정의합니다.

```json
{
  "skinName": "핀테크 B2B",
  "hue": { "brand": 255, "accent": 172 },
  "chroma": "muted",
  "radius": "sm",
  "elevation": "flat",
  "borderStrength": "strong",
  "density": "compact",
  "headingFont": "sans"
}
```

AI는 이 표의 칸만 채웁니다. 각 칸은 정해진 후보 중 하나입니다.
표에서 실제 CSS 변수 수백 개로 확장하는 것은 결정론적 함수의 일입니다.

함수가 책임지는 것: 명도 단계 생성, 대비 자동 보정(WCAG AA 이상),
보조색 산출, 여백 스케일 일괄 적용.

결과적으로 AI가 이상한 조합을 내놔도 **못생길 수는 있어도 망가지지는 않습니다.**
대비 미달, 색 충돌, 여백 불균형 같은 실패 모드가 구조적으로 차단됩니다.

## 핵심 결정 5 — 일탈을 금지하지 말고 라이브러리로 흡수시킨다

100%를 보장하려면 탈출구가 있어야 합니다. 없으면 디자이너나 개발자는
라이브러리를 우회해 처음부터 새로 짭니다. 그 순간 공통성이 진짜로 무너집니다.

그래서 탈출구를 열되 조건을 붙입니다.

- 계약을 유지하면서 렌더링을 완전히 갈아끼우는 것을 허용한다
- 단, 그렇게 만든 것은 새 프리젠테이션으로 레지스트리에 등록해야 머지된다

일회성 일탈이 재사용 자산으로 전환됩니다. 통제가 아니라 축적으로
공통성을 확보하는 방식입니다.

## 레이어 구성

| 레이어 | IA 대응 단위 | 예시 |
| --- | --- | --- |
| L0 토큰 | — | 스킨, 밀도 |
| L1 프리미티브 | (직접 안 씀) | button, input, card |
| L2 블록 | IA 하위 기능 | filter-bar, data-table, form-section |
| L3 페이지 원형 | IA 페이지 노드 | list-page, detail-page, form-page |
| L4 앱 셸 | IA 트리 전체 | sidebar, breadcrumb, 탭 내비게이션 |

L1은 shadcn 원본과 1:1로 유지합니다. 우리 취향을 넣는 순간 업스트림 업데이트를
따라갈 수 없고, AI 도구들이 아는 형태에서 멀어집니다. 차이는 토큰 레이어에서 냅니다.

L3이 에이전트 안정성의 핵심입니다. AI에게 버튼부터 조립하게 하면 결과가 매번
다르지만, "이 페이지는 목록형"이라고 원형을 먼저 고르게 하면 나머지는 슬롯 채우기가
됩니다. 판단 지점이 줄어드는 만큼 결과가 안정됩니다.

L4는 IA 트리가 곧 내비게이션 구조이므로 AI 판단이 거의 필요 없는 기계적 변환입니다.

## 배포 방식 — 레지스트리 + 샌드박스 템플릿

npm 패키지가 아니라 shadcn 커스텀 레지스트리로 배포합니다.
소스가 프로젝트 안으로 복사되므로 자유롭게 수정할 수 있고,
레지스트리는 MCP와 `llms.txt`를 지원해서 AI 도구가 우리 컴포넌트 목록을
인식한 상태로 코드를 생성합니다.

다만 에이전트가 부품을 하나씩 가져오게 하면 느리고 실패 지점이 많으므로,
컴포넌트가 전부 설치된 샌드박스 템플릿을 별도로 유지합니다.
에이전트는 그 안에서 렌더합니다.

문서 사이트가 레지스트리 호스팅을 겸합니다. 사이트 하나를 배포하면
사람용 카탈로그와 부품 배송 창구가 동시에 해결됩니다.

## 인정하는 한계

**토큰 교체로 흡수되지 않는 것이 있습니다.** "카드 목록을 칸반 보드로"는
디자인 변경이 아니라 정보 구조와 작업 흐름의 변경, 즉 IA 변경입니다.

이걸 디자인 단계에서 몰래 처리하면 IA 문서와 실제 화면이 어긋나고
후반의 혼선으로 돌아옵니다. IA 단계로 되돌려 스펙을 갱신하고 다시 렌더합니다.
스펙 기반이므로 되돌리는 비용이 낮습니다.

**페이지 원형의 표현력에는 상한이 있습니다.** 원형에 안 맞는 화면이 반드시
나옵니다. 그때 AI가 억지로 맞추면 이상한 결과가 나오므로, "원형에 안 맞음"을
에이전트가 명시적으로 보고하고 사람에게 넘기는 경로가 필요합니다.

**Base UI는 아직 1.0 RC입니다.** 접근성 구현은 Radix보다 낫지만 생태계는 얇고
API가 바뀔 수 있습니다. 버전을 고정하고 업그레이드 창구를 따로 둡니다.

## 진행 단계

| Phase | 목표 | 성공 판정 |
| --- | --- | --- |
| 0 | 틀과 안전장치 | 위반 코드를 올리면 CI가 실패한다 |
| 1 | 토큰 3계층, 스킨 3종, 컴포넌트 8개 | 극단 스킨에서 아무것도 깨지지 않는다 |
| 2 | 레이아웃 프리셋, 밀도 축 | 배치가 바뀌어도 계약이 동일하다 |
| 3 | 화면 스펙 스키마, 렌더러, 페이지 원형 3개 | 스펙 하나에서 와이어프레임과 디자인이 모두 나온다 |
| 4 | 컴포넌트 메타데이터, `llms.txt` | 같은 입력으로 3번 돌려도 결과가 크게 흔들리지 않는다 |
| 5 | 컴포넌트 30~40개, 원형 8개, 앱 셸, 목 데이터 | 실제 프로젝트 하나를 처음부터 끝까지 돌린다 |
| 6 | 일탈 보고 경로, 프리젠테이션 등록 프로세스 | 일탈이 라이브러리 자산으로 전환된다 |

Phase 1과 Phase 3이 전체의 성패를 가릅니다. 둘 중 하나라도 성립하지 않으면
그 시점에 구조를 바꾸는 것이 이후에 바꾸는 것보다 훨씬 저렴합니다.

## 제외한 것

**Figma 연동.** 목적이 "디자이너도 직접 디자인하지 않고 AI로 디자인을 완성하는 것"
이므로, 디자인 도구를 왕복하는 경로는 목표와 반대 방향입니다.
